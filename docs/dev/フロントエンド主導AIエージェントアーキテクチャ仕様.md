# フロントエンド主導 AI エージェントアーキテクチャ仕様書

## 1. 概要と背景

本ドキュメントは、**`novelaide`** における AI 執筆支援エージェントの通信・実行基盤について、**フロントエンド（WebView / React）をオーケストレーターの中核とし、必要に応じてバックエンド（Tauri Rust）を呼び出す構成**の設計仕様を定義するものです。

### 1.1 フロントエンド主導構成を採用する必然性

AI エージェントをバックエンド（CLI/Sidecar や Rust 単体）だけで完結させず、フロントエンドを経由させるべき決定的な理由は以下の 2 点にあります。

1. **未保存バッファ（リアルタイム原稿）の優先参照と編集**:
   - 小説作家がエディターで執筆している最中、最新の文章はディスク（ファイル）にはまだ保存されておらず、フロントエンドのメモリバッファ（Monaco Editor / DocumentContext）にのみ存在します。
   - バックエンドが直接ディスクファイルを読み書きするだけの構成では、作家がリアルタイムに入力した最新の推敲テキストや未保存の変更を取りこぼしてしまいます。
   - フロントエンドがエージェント通信のハブとなることで、**「未保存バッファの最新テキストを直接ツールに渡す」「必要に応じてフロントエンド側で一旦開いて差分比較（Diff Editor）を行ってから保存する」** といった柔軟な制御が可能になります。

2. **UI 状態・開いているドキュメント群との動的連携**:
   - 小説執筆では、「現在開いているタブ一覧（章原稿やキャラクター設定メモ）」「左右スプリットビューで参照中の資料」「現在のカーソル位置周辺」など、**UI に直接紐づくコンテキスト**が極めて重要です。
   - フロントエンド主導であれば、「開いているドキュメント一覧の取得（`get_open_documents`）」や「アクティブな原稿テキストの取得（`get_active_document`）」といった UI 連動ツールを自然かつ安全にエージェントへ提供できます。

## 2. アーキテクチャ設計

### 2.1 データフロー（フロントエンドがハブとなる構成）

```text
       ┌────────────────────────────────────────────────────────┐
       │                   フロントエンド (UI層)                 │
       │                                                        │
       │  [作家] ──入力──> [AIChatPanel / AIChatInput]           │
       │                         │                              │
       │                         ▼                              │
       │              [PiWritingAgentSession]                   │
       │                         │                              │
       │     ┌───────────────────┴───────────────────┐          │
       │     ▼                                       ▼          │
       │ [UI状態・未保存バッファ]                [novelaidExtension]   │
       │  - activeLeftItem (未保存原稿)            │                  │
       │  - activeRightItem (プレビュー/設定)       ├─ UIツール (直接解決)
       │  - openDocuments (タブ一覧)              │   - get_open_documents
       │                                          │   - get_active_document
       │                                          ▼                  │
       │                             [ToolProxy (IPCプロキシ)]       │
       └──────────────────────────────────────────┼─────────────────────┘
                                                  │ 必要時のみ呼び出し
                                                  ▼ (Tauri IPC)
       ┌────────────────────────────────────────────────────────┐
       │                バックエンド (Tauri Rust / FS)           │
       │                                                        │
       │  - 高速校正解析エンジン (proofread_scan)                 │
       │  - 高速ルビ抽出エンジン (ruby_suggest)                   │
       │  - Frontmatter メタデータキャッシュ検索 (search_metadata)│
       │  - ネイティブファイル I/O                              │
       └────────────────────────────────────────────────────────┘
```

## 3. 提供ツール仕様

### 3.1 UI・バッファ連携ツール（フロントエンド完結）

| ツール名 | 説明 | 引数 | 戻り値 | 処理内容 |
| :--- | :--- | :--- | :--- | :--- |
| `get_open_documents` | 現在エディターで開かれているドキュメント一覧を取得 | なし | `{ documents: Array<{ path, title, isDirty }> }` | `DocumentContext` の開いているタブ一覧を返す |
| `get_active_document` | 現在フォーカスされている原稿の最新バッファ（未保存含む）を取得 | `{ side?: "left" \| "right" }` | `{ path, title, content, isDirty }` | 編集中の最新テキストをメモリから直接返す |

### 3.2 高速解析・データ処理ツール（フロントエンドがRustを呼び出し）

| ツール名 | 説明 | フロントエンドの前処理 | バックエンド（Rust）処理 |
| :--- | :--- | :--- | :--- |
| `scan_proofread` | 文末重複・誤字・冗長表現スキャン | 引数省略時は `activeLeftItem.content`（未保存最新原稿）を自動補填 | Rust 側で正規表現・辞書パターンによるミリ秒スキャン |
| `extract_ruby` | 難読漢字・固有名詞のルビ候補抽出 | 引数省略時は `activeLeftItem.content`（未保存最新原稿）を自動補填 | Rust 側で漢字ルビ辞書・初出検出を実行 |
| `search_metadata` | Frontmatter設定資料のキーワード検索 | クエリ引数をバリデーション | `tauri-plugin-novelaid-fs` のメタデータキャッシュから高速検索 |

## 4. 将来の `novelaid-cli` / Sidecar 連携への適合性

* 本アーキテクチャでは、ツールのインターフェース（スキーマ・名前）が標準化されているため、
  - **novelaid-cli (CLI環境)**: そもそも UI が存在しないため、CLI 自身がカレントディレクトリやファイルを直接読み取って実行。
  - **Sidecar 連携時**: 将来 CLI を Sidecar 化した場合でも、フロントエンドが未保存バッファを把握し、Sidecar プロセスに対して未保存テキスト付きで解析リクエストを送信する形になるため、アーキテクチャの破綻が一切ありません。
