# 第44回：プロジェクト相対パス基準管理とファイルパス処理の完全撲滅

こんにちは！小説執筆用エディター **`novelaide`** 開発チームです。

エディターやIDEを長年開発・保守していると、コードベースのあちこちに **「ファイルパスをその場でスラッシュやバックスラッシュで split して末尾を取り出す」「正規表現で拡張子を削り取る」** といったローカル処理が静かに増殖してしまうことがあります。

```typescript
// 😱 あちこちに点在していたローカル処理の例
const fileName = path.split(/[/\\]/).pop() || path;
const ext = fileName.includes('.') ? fileName.split('.').pop()?.toUpperCase() : 'UNKNOWN';
const baseNameWithoutExt = fileName.replace(/\.[^/.]+$/, '');
```

Windows と macOS / Linux ではパス区切り文字（`\` と `/`）が異なり、各画面で場当たり的に文字列操作を行っていると、予期せぬエッジケースやタイポ、バグの温床となります。

今回は、これらの**ローカル文字列処理をプロジェクト全体から徹底的に撲滅**し、**「プロジェクト相対パス（`relativePath`）」を基準とした堅牢な内部管理アーキテクチャ**へと刷新した軌跡をお届けします！

---

## 1. 内部管理は「プロジェクト相対パス」へ

これまでの `novelaide` では、内部ステート（`DocumentState.path` など）に OS ネイティブな絶対パス（例: `D:\repos\my-novel\01_章\01_話.md`）がそのまま流れていました。

しかし、小説執筆エディターの内部ドメインにおいて、本当に重要なのは **「プロジェクトフォルダーから見てどの位置にあるか」という相対パス** です。

1. **可搬性とセキュリティ**:
   - 内部状態やログ、設定ファイルにユーザーのホームディレクトリやローカル絶対パスが散乱するのを防ぐ。
2. **将来のマルチワークスペース対応**:
   - 将来的に複数の作品フォルダーを同時に開く「マルチワークスペース」を見据えたとき、`projectPath` と `relativePath` の分離が不可欠となる。
3. **実ファイル I/O の局所化**:
   - ディスクへの読み書きを行う「システム境界」でのみ `absolutePath` を使用し、アプリ内部のコンテキストやタブ管理では正規化された相対パスで完結させる。

## 2. 複数パターンのパス・ファイル情報を事前格納

ローカル処理が生まれてしまう根本原因は、「その画面で必要な形式（拡張子なしのタイトル、親ディレクトリ、拡張子など）が、渡されたオブジェクトに含まれていない」ことにあります。

そこで、Rust バックエンド（`tauri-plugin-novelaid-fs`）の走査・読み込み段階で、**標準ライブラリ（`std::path::Path`）を用いてすべての形式を事前確定**し、データ構造に最初から格納してフロントエンドへ届ける設計に改修しました。

### 拡張された `NovelaidDocument` / `DocumentState`

```typescript
export interface DocumentState {
  path: string;                // プロジェクト基準の正規化パス（スラッシュ統一）
  relativePath: string;        // プロジェクトルートからの相対パス（例: 'episodes/01.md'）
  absolutePath: string;        // 実ファイルI/O用のOS絶対パス
  projectPath: string;         // 所属プロジェクトのルートパス
  relativeParentDir: string;   // 親フォルダの相対パス（例: 'episodes'）
  parentDir: string;           // 親フォルダの絶対パス
  baseName: string;            // ファイル名（例: '01.md'）
  fileTitle: string;           // 拡張子なしのタイトル（例: '01'）
  extension: string;           // 拡張子（小文字、例: 'md'）
  documentType: NovelaidDocumentType;
  content: string;
  // ...
}
```

Rust 内部でも正規表現や自前文字列分割は一切使わず、`Path::strip_prefix`、`Path::parent()`、`Path::file_name()`、`Path::file_stem()`、`Path::extension()` などの公式標準メソッドのみで確定させています。

## 3. 無理なフォールバックの完全撤廃

これまでの `fileService.readFile` では、万が一の未対応ファイルや読み込み例外に備えて、フロントエンド側の `catch` 節で無理にパスを文字列分解し、モックドキュメントを「でっち上げる」フォールバック処理が存在していました。

しかし、バックエンドが未対応バイナリや未知の拡張子であっても安全に `DocumentType::Unknown` として正規のオブジェクトを返すようになったため、**フロントエンドで無理なフォールバックを行う必要自体が完全に消失**しました。

```typescript
// 変更前: catch 節で自前パス分解してダミーを捏造
catch (err) {
  const fileName = path.split(/[/\\]/).pop() || path;
  return { path, name: fileName, ... }; // バグや不整合の温床
}

// 変更後: フォールバック処理自体を完全撤廃！
// バックエンドが安全に確定した NovelaidDocument をそのまま返す
const doc = await novelaidFs.readDocument(path);
return doc;
```

「フォールバックで救済する」のではなく、**「最初から破綻しないデータ構造にして、フォールバックの存在理由そのものを消す」** という設計判断により、コードが劇的にシンプルかつ堅牢になりました。

## 4. 全コンポーネントでのローカルパス処理の撲滅

事前格納されたプロパティと、`fileService` から公開された公式ユーティリティ（`basename`, `dirname`, `extname`, `stem`, `joinPath`, `isSubPath`, `normalizePath`）を活用し、全コンポーネントのリファクタリングを実施しました。

| コンポーネント | 以前のローカル処理 | 改善後の設計 |
| :--- | :--- | :--- |
| **`UnsupportedFileView`** | `path.split(/[/\\]/).pop()` | Props の `baseName`, `extension`, `absolutePath` を直接参照 |
| **`ImagePreview`** | `filePath.split('.').pop()` | `getMimeType(extension)` へリファクタリング、実パス解決に `absolutePath` 使用 |
| **`CodeEditor`** | `path.split(/[/\\]/).pop()` | `detectMonacoLanguage(path, type, extension, baseName)` で判定 |
| **`EpisodeNavigator`** | 自前の `getParentDirectory` と `normalizePath` | Props の `parentDir` を直接利用して同階層エピソードを走査 |
| **`StatusBar`** | `activePath.split(/[/\\]/).pop()` | `fileService.basename(activePath)` を使用 |
| **`BaseMetadataListPanel`** | `filePath.split(/[/\\]/)` と正規表現置換 | `fileService.basename` と `fileService.stem` を使用 |
| **`FileExplorerContext`** | 自前の `getParentDir`, `joinPath`, `isSubPathOrEqual` | `fileService` の公式パス操作関数群に完全統合 |

### 境界での絶対パス自動解決（`resolve_target_path`）の重要性

内部管理を相対パス（例: `01_プロローグ.md`）へ切り替えた際、1つ重要な落とし穴がありました。Rust バックエンドの `std::fs::read_to_string(path)` 等に相対パスがそのまま渡ると、OS はアプリ起動時のカレントディレクトリ（CWD）基準で探索してしまい、ファイルが見つからずエラー（Unknown判定）になってしまいます。

これを防ぐため、Rust プラグイン側に `resolve_target_path` を導入しました。
- 渡されたパスが相対パスなら、設定中の `project_directory` と自動結合して絶対パスへ解決
- 渡されたパスが既に絶対パスなら、そのまま使用

このハイブリッド自動解決をバックエンドの全 I/O 境界に敷設したことで、クライアント側が相対パス・絶対パスのどちらを渡しても、100% 確実に実ファイルへアクセスできるようになりました。
