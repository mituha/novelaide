# 第48回：なぜローカルAIの返信が遅いのか？思考トークン（Reasoning）のリアルタイム描画とモデル名解決の高速化

こんにちは！ 小説執筆用エディター **`novelaide`**（コードネーム: `novelaid-e`）開発チームです。

前回（第47回）は、Google Gemini（クラウドAPI）と LM Studio（ローカルLLM）を自在に行き来できる動的モデル選択基盤を構築しました。
しかし、いざローカルLLM（LM Studio / Qwen 3.5 2B）を使ってチャットをテストしてみると、思わぬ壁にぶつかりました。

> **「質問を送信してから、AIが返信し始めるまでの反応がかなり遅い……」**  
> 一方、先行して開発していたターミナル版エージェント `novelaid-cli` で同じモデル・同じ質問を投げた場合は、そこまで待たされずにサクサク返ってきます。

同じPC、同じLM Studio、同じモデルなのに、なぜGUIアプリ（`novelaide`）ではこんなにも返信までの時間がかかってしまうのか？  
今回は、LM Studio の詳細な通信ログを突き合わせて見つけた**「2つの決定的なボトルネック」**と、それを撃破した**「思考トークン（Reasoning）のリアルタイムストリーミング基盤」**の実装ドラマをお届けします！

---

## 1. LM Studio のログを比較して見えた「2つの異変」

まずは、LM Studio のコンソールに出力された「novelaide（遅い）」と「novelaid-cli（速い）」の受信リクエストログを並べて比較してみました。

### novelaide から届いたリクエスト
```json
{
  "model": "unknown",  // ← え……！？
  "messages": [
    { "role": "system", "content": "【執筆支援ペルソナ設定】..." },
    { "role": "user", "content": "こんにちは" }
  ],
  "stream": true
}
```

### novelaid-cli から届いたリクエスト
```json
{
  "model": "qwen3.5-2b",  // ← 正しいモデル名
  "messages": [ ... ],
  "stream": true
}
```

### 返答ログ（novelaid-cli）
```json
{
  "role": "assistant",
  "content": "こんにちは！お元気ですか？...",
  "reasoning_content": "The user is greeting me in Japanese (\"こんにちは\" means...)"
}
```

この2つのログを見比べた瞬間、すべての謎が氷解しました。

---

## 2. 原因①：`"model": "unknown"` による探索オーバーヘッド

最初の異変は、novelaide が送信していたリクエストボディの `"model": "unknown"` です。

### なぜ "unknown" になっていたのか？
novelaide では、Pi SDK のコアライブラリである `pi-agent-core` の `Agent` クラスを利用してセッションを管理しています。  
この `Agent` の初期化時、`initialState.model` を未指定のままインスタンス化していたため、ライブラリ内部のフォールバック用初期値である `DEFAULT_MODEL = { id: "unknown", ... }` が適用されていました。

ストリーミング関数側でも、渡されたオブジェクトの `id`（="unknown"）をそのまま信用してリクエストボディに入れてしまっていたのです。

### LM Studio 側で何が起きていたか？
LM Studio は、リクエストされたモデル名（`unknown`）と現在メモリにロードされているモデル（`qwen3.5-2b`）が一致しない場合、「指定されたモデルはどれだ？」とローカルディスクのモデルキャッシュを探索したり、オンデマンドのロード判定を走らせたりします。  
これが最初のリクエスト遅延（オーバーヘッド）を引き起こしていました。

---

## 3. 原因②（最大の体感遅延要因）：思考トークン（`reasoning_content`）の沈黙

しかし、モデル名解決のオーバーヘッド以上にユーザー体験を損ねていた「真の黒幕」が判明しました。  
それが、Qwen 3.5 や DeepSeek 等の最新推論モデルが持つ**「思考（Reasoning / Thinking）」の出力**です。

### Qwen 3.5 の二段階出力
Qwen 3.5 は、ユーザーの問いかけに対して即座に答えを出力するのではなく、回答を組み立てるための**思考プロセス（Reasoning）を先行して数十〜数百トークン出力**します。

LM Studio からは以下のような Server-Sent Events（SSE）チャンクが怒涛のように流れてきていました：
```json
data: {"choices":[{"delta":{"reasoning_content":"ユーザーは日本語で挨拶をしている..."}}]}
data: {"choices":[{"delta":{"reasoning_content":"適切な作家アシスタントのトーンで..."}}]}
...（百数十トークン続く）...
data: {"choices":[{"delta":{"content":"こんにちは！" /* ここから本文開始 */}}]}
```

### novelaide は思考トークンを捨てていた！
当時の novelaide のストリーミング受信コードを見てみましょう：
```typescript
if (delta?.content) {
  const token = delta.content;
  stream.push({ type: 'text_delta', delta: token, ... });
}
```
**`delta.content` しか見ていません！**  
つまり、AI が一生懸命「うーんと、挨拶だから親しみやすく返信しよう」と考えを巡らせている数十秒間、**novelaide 側はすべての思考トークンを無視して完全に画面を沈黙（フリーズ）させていた**のです。

思考がすべて完了して最後の最後、`delta.content`（「こんにちは！」）が出始めてようやく画面が動き出すため、人間の目には「質問してから返答が始まるまでに異常な時間がかかっている」ように見えていたのでした。

---

## 4. 解決策：思考の可視化と二重のモデル名防壁

原因がすべて明らかになれば、あとは鮮やかに解決するのみです。

### 1. モデル名の多重防壁
`PiWritingAgentSession` の初期化時に `initialState.model` へ現在選択中のモデルIDを確実に注入。さらに `createBrowserStreamFn` 側でも、万一 `id === 'unknown'` が渡ってきた場合は選択中のデフォルトモデルを採用する防壁を設けました。
これによって、LM Studio に確実に `"model": "qwen3.5-2b"` が届くようになり、探索の無駄時間がゼロになりました。

### 2. 思考トークン（Reasoning）のリアルタイムストリーミング
SSE チャンクから `reasoning_content`（または `reasoning` / `thought`）を検出し、Pi SDK（`@earendil-works/pi-ai`）の規格に完全準拠したイベントを送出するようにパイプラインを拡張しました。

```typescript
// 1. 思考トークン（Reasoning / Thinking）の検出と送出
const reasoningToken = delta?.reasoning_content || delta?.reasoning || delta?.thought;
if (reasoningToken) {
  if (!isThinkingActive) {
    isThinkingActive = true;
    stream.push({ type: 'thinking_start', ... });
  }
  stream.push({ type: 'thinking_delta', delta: reasoningToken, ... });
}

// 2. 本文トークンへの切り替え
if (delta?.content) {
  if (isThinkingActive) {
    isThinkingActive = false;
    stream.push({ type: 'thinking_end', ... });
  }
  stream.push({ type: 'text_delta', delta: delta.content, ... });
}
```

### 3. UI（`ChatView.tsx`）へのリアルタイム反映
チャット画面側では、思考トークンが届いた瞬間から `type: 'thought'` のパーツへテキストをリアルタイムに流し込みます。

すでに `ChatMessageList` には `<details className="chat-thought">`（思考プロセス）のUIコンポーネントが用意されていたため、**送信ボタンを押した直後から「思考プロセス」のアコーディオンが開き、AIがリアルタイムに考えを紡ぎ出す様子が目に見えるようになりました！**

思考を出力しない通常のモデル（または思考をスキップした場合）は、回答完了時に空の thought パートを自動クリーンアップするため、UIのノイズにもなりません。

---

## 5. まとめと次回予告

今回の改善により、以下の効果が得られました：
1. **LM Studio 側でのモデル検索オーバーヘッドの完全撤廃**（`"model": "qwen3.5-2b"` の正確な送信）
2. **「返信待ちの沈黙時間」の完全消滅**（思考開始の瞬間から0.数秒で画面が動き出す圧倒的なライブ感）
3. **AIの思考ロジックの可視化**（どのような意図で回答が作られたのかを作家が確認可能に）

「遅い」と感じる原因の多くは、単に計算時間が長いだけでなく、**「システムが何をしているのかユーザーに見えない（沈黙している）」**ことにあります。  
思考プロセスをリアルタイムにストリーミングすることで、体感速度と対話の安心感が劇的に向上しました。
