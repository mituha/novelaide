### ユーザー入力プロンプト
> AIエージェント関連の実装方法について検討、確認を行ってください。
> 現在、streamFnをオーバーライドしていますが、
> これは、pi sdk の実行がフロントエンド側でfsなどのOS固有機能が使用できないためと思われます。
> そのため、最終的にはバックエンドやSidecarでの動作が望ましいです。
> しかし、そのためにはnovelaid-cliのバイナリ実行が必要となり、現段階では開発上かなり手間がかかります。
> そこで、将来的な移行も考慮して、現段階で最適な構成を再検討します。
> 
> Pi SDKにおいては、最終的に機能拡張(Extension)によりTool、Commandを登録、処理しています。
> つまり、これらのToolをどこで実装するかだけの問題です。
> 
> Toolの中身をIPCで通信をするプロキシとするか、中身のある自身での処理とするかで切り替えることが可能です。
> 最終的なnovelaid-cliであれば、起動モードによって切り替えれば良いことになります。
> 
> このような実装とすれば、最終段階での移植は最低限で済む構造が採れると考えられます。
> novelaide側、novelaid-cli側で登録するツールやコマンドのインターフェースだけをそろえておけばよい
> 
> また、現在のツールの扱いはまだregisterToolを使用するようになっていません。
> また、コマンドに関してはTUIではないため、事前に割り込んだ処理が必要かもしれません。
> なるべく、Pi SDKの標準機能を使用する方向で再検討、見直しを行ってください。

     - `api.registerCommand` により CLI（`novelaid-cli`）と同一のスラッシュコマンド（`/ruby`, `/proofread`, `/check`, `/info`, `/help`）を登録。

     - スラッシュコマンド（`/` で始まる入力）の事前インターセプトメソッド `executeCommand` を実装。
     - チャットプロンプト送信時に `/` コマンドを検知した場合は、LLM API リクエストを発生させずにローカルコマンドハンドラーを実行し、その結果をメッセージタイムラインに即座に表示。

### 設計上の判断理由
- **「プロキシ」と「実体」の切り替えによる究極の可搬性**:
  将来 `novelaid-cli` を Tauri の Sidecar（子プロセス）やバックエンドとして移行する際、Extension の Tool インターフェースが完全に揃っているため、フロントエンド側は IPC 呼び出し先を差し替えるだけで済み、UI や Extension 自体の書き直しを完全に不要とした。

  TUI 向けに作られたスラッシュコマンド体系を GUI チャット入力でも事前割り込みで実行できるようにしたことで、作家がキーボードから手を離さずに `/ruby` や `/proofread` を即座に実行できる操作性を実現した。

### 設計上の判断理由
- **未保存原稿を絶対に欠落させないエディター特化アーキテクチャ**:
  作家がリアルタイムに執筆・推敲しているテキストは、保存されるまでフロントエンドのメモリ上にのみ存在する。バックエンドがディスクファイルを直接参照する構成では未保存テキストを取りこぼしてしまうため、フロントエンドがオーケストレーターとなり最新バッファをツールに渡す構成が必然かつ最善である。
- **UI 直接解決とバックエンド高速処理のハイブリッド構成**:
  タブ一覧やフォーカス原稿の取得はフロントエンド完結でオーバーヘッドなく即座に解決し、形態素解析や正規表現スキャンなどの重量処理のみを Rust ネイティブプラグインへ委譲することで、最高速のレスポンスと高い拡張性を両立した。
